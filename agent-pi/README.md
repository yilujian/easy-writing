## Skill 真实流程专项测试 2026-10-23—24

使用平台当前选中的 DeepSeek v4 Pro，在隔离 Tauri 配置中上传作者指定书籍；按作者调整只蒸馏第 1—15 章，输出 Skill 后由模型自主构思《镇魂钟表店》并写出 5 章。未人工提供人物、章纲或正文，未修改生成的 Skill。书名、计划、每章候选均来自同一真实模型会话，逐章通过平台采用。

- 产物：60 段范例、20 条写法卡、8 条叙事模式。60 段范例均能在源文匹配，来源覆盖第 1—15 章，卡片引用有效。最终书库恰好 5 个非空章节，正文与模型候选逐字一致，Skill 文件哈希未变化。
- 修复首章进度：新作品默认有空白首章，模型使用 `save_draft` 填写时，批量流程曾误报没有候选。统一识别新增章和空白章的首次填写，核对会话、作品、轮次与采用状态；继续前核对已经采用的正文，避免重复生成。修改已有正文不计入新增章。
- 修复技能更新：`--skill` 是进程启动时固定的路径列表，`ctx.reload()` 无法加载后来新增的文件，也无法正确应用启停。下一次作者消息或平台事件前保持原会话重连，重新读取启用列表。真实 UI 新建 Skill 后，同一会话的 Pi 记录已出现 `<skill>` 展开，Pro 返回指定验证标记；停用后运行时命令列表不再包含它。
- 验证：Pi 相关前端 37 文件、221 项测试通过，`vue-tsc --noEmit` 通过。蒸馏曾在第 2 章超时，正常重试一次后从检查点完成；验证期间因修复平台及测试脚本恢复过运行环境，不能称为无中断一次成功。
- 内容观察：范文能体现旁观侧写、对白介绍设定、章末悬念等写法，但能力扩展缺乏铺垫，“三天后取表”的时间线存在矛盾。这是保留原始输出后的人工阅读结论，未用自动分数或模型自评宣称质量合格。

## 真实模型多措辞验收与修复 2026-10-23

按作者授权，使用开发版平台已启用的 DeepSeek v4 Flash 和 Pro，在隔离作品与 Pi 会话中测试；来源模型库只读，临时复制到隔离配置的模型记录在结束后恢复。没有连接真实微信账号或发送消息，没有改正式作品、妙笔和自动任务。

- 最终验收：每个模型 25 个用例，共 **50/50 通过**。覆盖三种“记住”、两种“纠正”、两种“忘记”、作品事实、取消保存/删除、临时要求、小说引文、新会话回忆、作品隔离、本轮要求优先、分步卡、附加输入、规划阶段选范围、多选、四种改稿/待批准措辞、仅审稿、仅聊天示例。用实际工具调用、确认前后记忆和正文版本判定；不以模型口头声称保存作为成功。
- macOS 工具桥偶发 `ECONNRESET`：非阻塞监听器的 accepted socket 继承了非阻塞模式，独立处理线程可能在请求尚未到达或分包时收到 `WouldBlock` 并关闭连接。`configure_tool_stream` 显式恢复阻塞读取，并保留 10 秒请求读取超时。独立实验及延迟/分包原生回归已验证；没有用重放写操作掩盖断连。
- 候选交付缺失：真实模型曾把“确认后再保存/等批准再采用”理解成只在聊天贴正文。澄清候选提交与正式采用的契约，并为 `read_chapter` 增加必填 `purpose`（revision/review/context/example）。模型声明 revision 后，扩展登记待交付章节；Pi 原生 `agent_before_settle` 在漏交时追加一次隐藏交付检查并继续原生执行。再次漏交明确报错；取消、错误、已存在续轮、保存冲突不会由检查自动重放。仅审稿、取上下文和明确只要聊天示例不触发检查。平台不解析作者原话猜意图，不自动提取聊天正文，不自动采用。
- 规划与执行混淆：只要求选择范围时，模型曾要求先上传附件。系统与询问工具契约明确区分收集选项和执行任务，不为尚未授权的执行阶段提前索要附件。用原句和另一种规划表述复测通过。

## 第 7 步：记忆与微信接入 2026-10-23

本轮按作者最新决定只做记忆与微信。妙笔不接 Pi 对话组件；自动任务暂不开发。原有妙笔、旧 Agent、自动任务及其通知实现保持原样。微信的协议客户端与扫码绑定沿用原实现，对话入口改由 Pi 执行，旧 Agent 微信会话不迁移。

### 记忆

- 宿主 `pi_memory.rs` 独立使用 `ew-agent-pi/memory`，分作者偏好（跨作品）与作品事实（绑定作品），保存/删除校验修订，跨作品编号、空内容、失效作品不会写入。每条最多 1200 字，每个范围最多 100 条。
- `pi_context.rs` 在每轮模型调用前读取当前作者与当前作品记忆，通过已有 Pi `context` 事件注入。上下文限制为 12000 字并显式返回省略数量；`read_memory(query)` 可检索完整存储，不静默把其他作品带入。
- `remember_memory` / `forget_memory` 先读取待修改内容和修订，再发作者确认卡；取消不改变记忆，版本改变则拒绝旧确认。模型不把临时任务、未采用候选或猜测自动存为事实。当前作者指令与正式资料优先于旧记忆。
- Pi 侧栏新增记忆页，可以查看、新增、编辑和删除作者偏好及所选作品事实。故事状态账本继续负责逐章剧情状态；没有导入旧 Agent 的记忆或增加自动提炼流水线。

### 微信

- `use-pi-workspace.ts` 增加独立于页面的入口方法，复用原 Pi 实例、工具执行、取消、保存与退出协调。微信通过 `weixin-adapter.ts` 映射消息、问题与候选，不挂载 Pi 对话组件，不切换桌面正在看的会话，沿用微信独立模型选择。
- 会话按微信绑定身份和新会话序号关联 Pi 原生 JSONL，映射保存在设置中；重启恢复同一会话，停止只影响该微信对话。首条消息前 Pi 尚未创建 JSONL，不提前读取不存在的文件；相同模型和作品不重复重启实例。
- 引导卡转编号文字，保留说明、批量目标、范围、脚本与封面信息；分步提问逐问推进，补充输入保留完整文本。回复 `/跳过` 可跳过分步的一问，`/取消` 取消当前卡。
- 候选发送预览和全文文件；采用绑定展示时的修订与原生确认票据。内容或卡片变化后必须重新展示，旧确认不能保存新内容。采用复用原子保存、回执与批量推进；暂不采用只搁置候选。
- `/停止` 优先处理，不被正在等待模型的消息堵住；新对话先停止旧会话。对话期间的后台任务完成续答按 Pi 事件投递，不新增调度器或自动任务。
- 这里的后台执行是“不打开 Agent 页面也可工作”。应用的主 Webview 与宿主进程仍需运行；没有实现应用退出后的守护进程，也不声称完成纯 Rust、无 Webview 的全工具执行器。

## 故事状态账本 2026-10-23

写新章只读前两章，到几十章时设定、数值、伏笔靠读两章读不回来。账本是第三层：每本书一份，每章采用后由模型提炼一条记录，并维护一份到最新一章为止的"当前状态"，写新章时随作品资料给模型。

- 数据（`src/agent-pi/story-ledger.ts`，记录库 `ew-agent-pi-ledger/ledger`，键 `book:<bookId>`）：每条记录有章节、提炼时的正文版本、摘要、状态变化、线索（open/resolved）、本章之后的状态、以及"本章之前的状态"的指纹。记录按章节顺序成链：某章重新采用或手改，它和它之后的记录依次重算（指纹对不上就重算）。一本书第一次用只从最后 3 章开始记，之前的章标为未记录。整理按书串行；失败（没模型、模型出错）不拦写作，原因记在账本上。
- 触发：章节采用后后台整理（`notifyChapterSaved` → `scheduleLedger`）；`read_references` 先把账本整理到最新再返回（宿主把它列为长工具），返回里多一个 `story`：当前状态、记录从第几章起、最近 5 章记录、还没整理的章、失败原因。书桌里手写的章在下次 `read_references` 时补提炼。
- 作者手改：右栏"故事状态"面板（页头书签按钮，`StoryLedgerPane.vue`）可改当前状态，改动锚在最新一条记录之后，下一章以它为前提；改回和模型一致就等于撤销。面板还列每章记录（新的在前）、还没整理的章、整理进度。
- 提示词在提示词库新文件 `story-ledger`（系统设定、输出结构、补充要求、任务），构造器 `src/config/story-ledger-prompts.ts`；模型用 Agent 当前选的文本模型（`ew-agent-pi-model`）。系统提示和 `read_references` 描述写明：写新章以 state 为准，pending 的章有疑问读原文。
- 测试 `tests/pi-story-ledger.test.ts` 4 项：从最后三章起记且成链、中间章重采用后链式重算、作者手改作为下一章前提与撤销、没模型时不拦写作且资料读取带故事状态。
- 没做：作者手改之后前面章节重算时，手改仍作用在原位置（设计如此）；一本旧书想把前面的章也记进去没有入口。

## 写新章的前情核对与材料核对 2026-10-23

真实对话里第 1、2、3 章接不上：第 1 章采用后作者要求换风格，模型把第 1 章改稿和第 2 章候选都重写了一遍，两份都停在"待采用"；接着批量从第 3 章写，模型读到的第 1 章是旧版正式正文，第 2 章工具根本读不到；人物设定卡也没采用，资料表是空的。规则"候选必须采用才算数"没错，漏的是写下一章时平台不检查上一章定没定。

- 前情核对（宿主、平台、扩展）：`save_new_chapter_draft` 保存前核对目标卷末前面的章节。上一章有针对当前版本、没采用也没搁置的改稿，或有比最近一次采用更新的新章候选，就不保存。扩展先用 `check: true` 向平台要核对结果，平台给出问题、选项和每个选项对应的处理（采用某份、搁置几份、先停下），扩展只负责把卡发出去、把选择用 `resolve` 交回，直到平台说 ready。采用走和右栏同一条路（`applyPiDraft`，并通知任务层）；搁置是宿主新操作 `dismiss_draft`（草稿加 `dismissedAt`，右栏照常显示、仍可采用，只是不再当作上一章；批量挑候选时也跳过搁置的）。`run_batch` 启动前对起点前一章做同样核对，没指定卷按最后一卷。
- 材料核对（平台）：保存新章时，目标卷末前面最近两章的当前版本必须在本对话里用 `read_chapter` 读过（版本号对得上，采用了新版就得重读），作品资料必须用 `read_references` 读过；人物、设定、大纲有采用时各对话的资料读取作废。没读就退回一句说明让模型读完再保存，不靠模型记得读。
- 契约与系统提示同步写明。测试：`tests/agent-pi-new-chapter.test.ts` 加 4 项（没读不让保存、旧版作废、候选与改稿的核对和搁置、按最后一卷），`tests/agent-pi-research-confirm.test.ts` 加 1 项（扩展编排：核对→卡→交回→放行；先停下不保存；批量启动前核对），卷归属与批量用例按新序列调整。
- 没做：第三层"故事状态账本"（每章采用后提炼发生了什么、数值物品关系变化、钩子，写下一章时注入）等作者决定。

## 一问一答：任务完成后接着说的那轮并进同一条回复 2026-10-23

拆书这类后台任务在模型启动后这一轮就结束了，任务跑完由平台代作者发一条事件，模型再开一轮读结果说结论。此前聊天里因此是两条回复（第一条"已开始拆解"加任务卡，第二条过程区加结论），作者只问了一次，答案却分两条。

- 数据层 `src/agent-pi/conversation.ts`：`PiTurn` 加 `rounds`（`PiTurnRound`：开始这一轮的事件、过程区、正文段、结论、文档、错误、运行与停止状态），各汇总字段（segments/steps/operations/drafts/answer…）照旧，是所有轮的合计。`buildPiTurns` 多收一个 `tasks` 参数（只要 id、callId、anchor）：平台事件开始的一组消息，若事件种类标为"接着说"且它的任务是由上一条回复里的工具调用（没记调用时按发起它的作者消息）启动的，就并进上一条回复成为新的一轮；否则仍是独立一条。事件种类表 `EVENT_KINDS` 同时给出标签文字和是否接着说：拆书、蒸馏、封面完成接着说；批量写作每章（`batch_chapter`）和收尾（`batch_completed`）各自一条，这是作者定的，每章是独立的交付。中间作者聊过别的、任务记录还没加载、任务在别的对话启动，事件都不并，照旧显示标签加独立回复。
- 视图 `PiConversation.vue` 按轮渲染：每轮各有过程区（抽成 `PiProcessBlock.vue`，标题与图标逻辑随之搬过去）、正文与引导卡、文档卡、任务卡（放在启动它的那一轮）、错误与停止提示；第二轮起在轮首显示事件标签（`.pi-event-chip.is-round`）；头像、分割线、复制按钮一条回复只有一份，复制的是所有轮的正文。原生询问卡只挂在最后一轮。去掉了昨晚只去头像的 `is-continuation` 样式。
- 测试 `tests/pi-process-steps.test.ts` 加 1 项：并入、无任务记录或任务不在这条里不并、按 anchor 认、中间聊过别的不并、批量不并、续轮运行中时第一轮不转圈。

## 蒸馏改为写作方法档案 2026-10-25

起因：用《我在精神病院学斩神》前 15 章蒸馏出的 Skill 写《镇魂钟表店》5 章，没学到剧情结构、爽点、钩子、铺垫。核实的原因：流水线只按 7000 字分段挑"好片段"（六种场景类型），没有章级、书级阅读；写作时 `examples.json` 只在起书名那轮被读过一次，批量事件不带技能。诊断与方案见 `易创工坊/样稿/Skill专项测试-20261023/蒸馏Skill问题诊断与升级方案-20261025.md`。

- 流水线（`src/agent-pi/distillation-tasks.ts`）改为三层：① 每章一次调用读整章出章卡（事件、章首承接、章尾钩子类型+原文、爽点类型与强度、埋下/回收的伏笔、新放出的设定与载体、人物功能）并按功能类型标范例（程序取原文；超过 12000 字的长章才分段，章卡由程序合并）；② 看全部章卡做书级归纳（核心梗、读者承诺、主角立法、金手指、配角功能、开篇任务、剧情单元、伏笔账本、钩子与爽点节奏、设定释放），每 40 章一批多批再合并；③ 看范例原文归纳写法卡（【功能类型】什么时候用→怎么做→效果）并核验。程序算 15 项语言指纹（`style-fingerprint.ts`）、钩子分布、爽点曲线、章均字数与对白占比。编档：SKILL.md 分节（卖点与人设 / 结构骨架 / 写法卡 / 叙事模式 / 范例库），`references/examples.json`（v3，带 kinds）+ `references/structure.json`（书级归纳、章卡、曲线、指纹）。导入正文章尾的"作者有话说"等留言在读之前剥掉（`TRAILER_MARKERS`）。

## 第二轮真实测试的四个根因 2026-10-25 深夜

## 技能名里的空格让技能根本没展开 2026-10-26 晚

用户用第三版蒸出的技能写了一章，会话里技能标签只显示到"《我在精神病院学斩神》都市异能热血成长写法（第"，"1—28 章）"掉进了正文。根因不是样式：Pi 的 `/skill:名字 正文` 命令按第一个空格切名字（`agent-session.ts::_expandSkillCommand` 用 `indexOf(" ")`），默认技能名的范围后缀"（第 1—28 章）"带空格，Pi 找不到技能就把整条消息原样发出，技能没有展开，那一章是在没有技能的情况下写的；我们这边 `parseSkillCommand` 也用 `\S+` 切，所以标签截断。修法是让技能名不再有空白，各层一起改：

- 宿主 `pi_skills.rs`：`compact_name` 去掉全部空白；`save`、`adopt`、`import` 的名字都先去空白；`list` 读到作者目录里名字带空白的旧文件（早期蒸馏的默认名）时顺手改写 SKILL.md，Pi 下次启动加载到的就是无空格的名字。`pi_distillation.rs::prepare` 的默认技能名去空白（"《长书》写作方法（第1—10章）"）。
- 前端 `skills.ts`：`compactSkillName`；`skillCommand` 发命令前去空白；`findSkill` 先精确再忽略空白对一次（老批量任务记的名字还能找到）；`parseSkillCommand` 对 `/skill:` 开头的老消息先按已知技能名忽略空白逐字对上再切正文，对不上才退回 `\S+`；`conversation.ts::stripAttachmentMarker` 走同一解析。`skillNameFor`、`research-tools` 的 skillName、`skill-draft.ts` 的候选名都去空白。
- 测试：`pi_host::skills::tests::skill_names_never_keep_whitespace_and_old_files_are_fixed_on_list`、`tests/pi-style-tools.test.ts` 加解析与查找一项、`pi-distillation-runtime` 技能名用例改为无空格格式。
